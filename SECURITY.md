# Security

MemoryNet is a local pilot build for synthetic and public test data. There is no production-supported hosted deployment or security maintenance guarantee at this stage.

## Trust boundaries

- The web server binds to `127.0.0.1:3050`. Keep it local; do not expose it through a reverse proxy, tunnel, or shared host.
- In local mode, a matching setup profile or prepared configuration supplies one fixed human operator. The app opens without sign-in; anyone with access to this local app can act as that operator. Session cookies, origin checks and CSRF checks still protect mutations. Persona switching and System controls are disabled. Existing key or GitHub login gates stay enabled unless `MEMORYNET_AUTH_MODE` explicitly changes the mode.
- In sandbox mode, the person picker is not authentication. Anyone able to use the app can choose a principal, including an administrator. Domain role checks do not establish that person's identity.
- In GitHub mode (the default with `MEMORYNET_GITHUB_CLIENT_ID` set unless overridden), sign-in uses the GitHub OAuth device flow. A session is bound to the person an operator linked to that numeric GitHub ID (`npm run github:link`); unlinked accounts are refused, and persona selection, the access key and System controls are off. Repository read access is checked with GitHub at sign-in and every 5 minutes, counts for 15 minutes, and access declared before startup is ignored. GitHub tokens stay in server memory only. Roles and organization membership are still local, and the server must still stay on `localhost`. See [GitHub sign-in](docs/prototype.md#github-sign-in).
- Explicit `MEMORYNET_AUTH_MODE=local` with a GitHub client ID enables optional account connection only. Connecting, revoking or disconnecting that account does not change local workspace access or refresh repository permissions.
- A separately configured local prototype hashes an owner-only access key and binds sessions to a configured human principal/GitHub numeric ID. It disables persona switching and System fixture endpoints. This verifies possession of a local key and database/config consistency, not current GitHub identity or organization membership. It is not multi-user authentication.
- `npm run app` auto-detects ignored `.local/prototype/config.json`; its database overrides `MEMORYNET_DATA_DIR`. Use `MEMORYNET_PROTOTYPE_CONFIG=off` for explicit isolated sandbox trials. Other scripts do not load prototype config or `.env.local`; set their actual database directory explicitly. See [mode configuration](docs/prototype.md).
- Sandbox System pages simulate trusted integration events; they are disabled in configured prototype and GitHub sign-in modes. A GitHub App with signed webhooks, permission synchronization for people who are not signed in, hosted identity, and remote MCP authorization are not implemented.
- Core repository-access freshness defaults to 15 minutes, which GitHub sign-in uses; without it the local app extends freshness to 30 days for fixture use. That extended mode is unsuitable for live organizational access control.
- Local MCP uses an expiring bearer credential in an owner-only file. A copied credential remains usable until expiry or revocation. It does not grant database roles or repository access. See the [interface contract](docs/agent-context.md).
- Version 2 bindings name their capabilities. With `propose` or `report`, an agent can create pending proposals, pull request evidence records and outdated-reports in its bound scope; it can never approve, suspend, revoke or administer. The project review policy can turn agent proposals off or cap them. Pull request excerpts an agent records are its own assertions, labelled as captured by the agent; reviewers must check them against the pull request.
- `npm run setup` declares repository access for the people and agent it creates, and `npm start` renews declarations that are still granted unless GitHub sign-in is configured. These are local statements, not GitHub permission checks. Client MCP files written by `npm run connect` hold local paths only; the credential stays in the binding file.
- The audit ledger makes edits made around database triggers detectable, and checkpoints stored elsewhere make a full rewrite detectable. Anyone who controls the database files can still destroy or rebuild history; the ledger proves tampering, it does not prevent it. See the [trust model](docs/trust.md).
- Instruction-like, personal-data and secret checks are bounded heuristics. Evidence and memory text are always data for agents, never instructions; MCP responses and server instructions say so.
- Model extraction sends selected evidence to Meta after an explicit action. The attempt allowance resets on restart and is not a durable spending limit. Provider text and source evidence are untrusted; citations still need human review.
- Databases, retrieval records, and exports can contain evidence text and query information. Offline backup/restore is available; backups contain the entire database, are not encrypted, and require the same pinned PGlite version to restore. Record-level deletion and retention are not implemented. See [local operations](docs/local-operations.md).
- Local HTTP requests have bounded headers, bodies, and upload time; Host and same-origin/CSRF checks protect the browser boundary. These checks do not replace authentication or protect against another process running as the same OS user.
- File-backed databases use a process ownership lock. Startup reclaims a crashed process's lock only when it can prove the owner stopped on this computer; live, foreign, or ambiguous ownership remains locked. Older versions and external database tools do not participate in this lock.

The public evidence downloader accepts only active public repositories. Do not adapt it to ingest private/internal evidence before the [private/shared-use prerequisites](docs/production-readiness.md) are met. Pinned source browsing validates configured origin and commit checks; it is not live repository permission verification.

Use `.env.local` or the in-memory settings form for model keys. Keep `.data/`, `.local/`, credentials, bindings, raw logs, and private development notes outside version control. Ignore rules do not remove files already committed or erase their history. Share a reviewed Git checkout rather than a copy of the entire working directory.

## Reporting a vulnerability

Use the repository's **Security → Report a vulnerability** option if the maintainer has enabled private reporting. If no private channel is available, open a minimal issue asking the maintainer for a private contact method without including exploit details or sensitive data. Do not put keys, private evidence, tokens, or affected users' data in a public issue.

Include affected revisions, reproduction steps using synthetic data, expected and observed behavior, and likely impact. Never send a live credential as proof. No response-time commitment is currently published.

## Local checkout discovery

Use only explicitly selected public or synthetic repositories on a stable, trusted filesystem. Preview reads bounded Git metadata through a temporary bare repository. It ignores the checkout's Git configuration for object access, disables network transports and never executes checkout hooks or scripts. It checks object-store entry types and rejects alternates and links. Imports read only the selected committed blob, check its entire text for recognized secrets and keep a hash plus excerpt. Free-form Markdown can still contain sensitive information or instructions. A malicious same-user process changing directories during inspection is outside the trust boundary.

The local reader has its own project database and exact-branch binding. An explicit public upstream attachment declares source access inside that database. Revocations in other isolated databases do not propagate. Revalidation checks current role, binding, current evidence and historical cited evidence. Permission loss can withhold the entire report. Previously downloaded responses and backups can still contain historical text.
