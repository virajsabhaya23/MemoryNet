Run MemoryNet locally.

Try reviewed decisions and changing requirements with a public repository, then connect a coding agent.

See a decision change first

Open the three-minute read-only replay, or run npm run demo after installing dependencies. It generates .local/decision-demo/index.html and a JSON report using a temporary database. It uses scripted extraction and fixture approvals, real MCP clients, and actual stale-export checks. It makes no external API calls and does not open your existing workspace.

Install the source

Use Node.js 24 or newer, npm, and Git. Start from a MemoryNet source checkout or exported source distribution and run these commands in its root directory. Get the source from the MemoryNet repository.

Terminal
npm ci --ignore-scripts
npm run check
MEMORYNET_AUTH_MODE=sandbox MEMORYNET_PROTOTYPE_CONFIG=off MEMORYNET_DATA_DIR=.data/first-trial npm run app

Open http://127.0.0.1:3050. In this isolated development sandbox, choose System → Load synthetic example data, then select a test person. A model account, API key, and database server are not required. The picker lets anyone at this computer act as these local principals; it is not authentication.

The app creates .data/first-trial/. Keep it on loopback and stop it with Ctrl+C before another process uses the same database. These shell examples work in macOS/Linux shells; on other shells set the named environment variables before running the command.

Local configuration: a clean checkout starts the development sandbox. A workspace created by npm run setup opens as its configured local operator with npm start. Existing GitHub and access-key gates remain enabled; MEMORYNET_AUTH_MODE selects a mode explicitly. An optional .local/prototype/config.json selects access-key mode, a configured operator, a database, and pinned source checkouts. Its database overrides MEMORYNET_DATA_DIR; MEMORYNET_PROTOTYPE_CONFIG=off disables prepared configuration and MEMORYNET_AUTH_MODE=sandbox explicitly selects test personas. Optional GitHub sign-in replaces the picker and disables System fixture controls; see docs/prototype.md.

Try your personal public repository

MemoryNet runs alongside your repository. Installing it does not change your code, create commits, or install a GitHub App. The current importer takes a one-time snapshot of public repository metadata and merged PR text; it does not continuously index code or synchronize future changes.

  1. Install the GitHub CLI and sign in with gh auth login. Stop the earlier trial app before starting the next one on port 3050.
  2. Replace YOUR_OWNER and YOUR_REPO below with your GitHub account or organization and repository name. Keep the new database separate from any existing workspace.
npm run data:download:evidence -- --owner YOUR_OWNER --repos YOUR_REPO --prs 20 --out .data/public/my-repo-evidence.json
MEMORYNET_DATA_DIR=.data/personal-trial npm run data:import:evidence -- .data/public/my-repo-evidence.json
MEMORYNET_PROTOTYPE_CONFIG=off MEMORYNET_DATA_DIR=.data/personal-trial npm run app
  1. Keep the import summary's owner, reviewer, importer, project, and organization IDs. Open the app and select the local workspace owner or reviewer from the picker. These roles are local test assignments, not proof of upstream GitHub membership.
  2. Open your project and inspect its sources. Depending on PR labels and titles, the importer may also create pending candidates; it approves none. With no merged PRs, capture an exact public source manually on the project page.
  3. For guidance that an agent or task can use, create a new proposal citing the source. Set its numeric GitHub repository ID, exact branch, and UTC validity interval. Imported heuristic candidates have no reviewed applicability; approving them alone does not make them eligible for scoped MCP or Affected work.
  4. Use a different local human principal to review and approve the exact revision. In this single-operator sandbox, switching principals exercises the permission checks; it is not an independent two-person review. Then follow the decision-change and MCP steps below.

The importer refuses to load the same owner snapshot twice into one database. Use a new explicit database directory for a later snapshot. It does not clone repositories or provision the original-source browser shown in the configured Vercel screenshots. A local Git checkout is needed only for source browsing configured separately or committed-file reconciliation.

Try it for a work repository

For a public work repository, use the same snapshot workflow within your organization's policies. To evaluate a private work scenario today, recreate one decision and a small task with synthetic or already-public material. Use an isolated local database and compare it with your team's existing ADRs and maintained instructions.

Private personal and private work repositories are outside the current supported pilot. The downloader deliberately skips private and archived repositories. Shared authentication, verified GitHub ingestion, live permission updates, deletion/retention, and approved external-model processing remain prerequisites for confidential workloads. The private-key prototype does not supply these missing organizational controls.

A useful trial asks: when an API rule changes during implementation, does the affected-work warning prevent a stale spec or agent handoff, after counting setup and review time? Choose one real problem represented with permitted data; a larger imported graph alone does not answer that question.

From your organization to one decision

Open an organization and choose Open the network. The map groups projects inside business units, with organization-wide guidance at the center. It connects memories, rules, instructions, skills, agent definitions, their owners, and source evidence.

  1. Find your project. Select its group and choose Only this group, or use the search field to find a named record. Drag to pan, scroll to zoom, and use the breadcrumbs to move back through the organization.
  2. Follow a connection. Hover to preview a neighborhood; select a node to inspect its owner, status, and current version. Choose Where did this come from? to trace supporting memories and pull requests, or What depends on this? to see connected definitions that rely on it.
  3. Maintain the record. Choose Open its page to review its evidence and version history. Propose a change for a separate authorized reviewer. The record pages preserve earlier versions when guidance is revised or replaced; ownership and role controls follow the selected scope.

Your network starts with you and the places you can access. It distinguishes your own role from access inherited through an organization or business unit. Open a place to expand its knowledge, then follow its link to the project page. Administrators can manage roles at the organization, business-unit, or project level.

Use ⌘ + K or / to search the full map, the arrow keys to move between items, and Enter to select. The Table view and the list below the map provide the records without the diagram. Filters and saved views help return to a particular area; saved views stay in your browser.

Tasks are tracked separately under a project’s Affected work page. Agent definitions describe their responsibilities and instructions; the map does not run agents. The homepage shows screenshots of the separately configured Vercel prototype, using original repository checkouts and public PR evidence. The website itself does not provide a live application or connect to your records.

Try one decision change

  1. Capture evidence. Add a public source with its exact revision, then create a new decision proposal with a repository, exact branch, and UTC validity interval.
  2. Review the exact version. Inspect the source and approve the exact proposal revision as a separate authorized human principal. In a real team trial, a different person must perform that review.
  3. Link active work. Open Affected work in the project. Create a task with its spec/file hashes and pin the approved decision version.
  4. Change and revalidate. Propose a revision, review it, then reopen Affected work. The old baseline needs review and cannot be exported as current context.
  5. Check the implementation. Refresh the task’s context and run the repository’s behavior tests. Fresh context and matching hashes do not prove that code follows a decision.

For a reproducible isolated check, run npm run eval:work. It uses automated synthetic fixture approvals and makes no model calls.

Connect a coding agent

The quickest path creates a separate workspace for one GitHub repository, a reviewer, a coding agent and its MCP configuration in one step. Run it in the MemoryNet source directory; --client also accepts claude, cursor or codex:

npm run setup -- --repo OWNER/REPO --reviewer "A teammate" --client vscode --project-dir ../REPO
npm start
npm run doctor -- --project-dir ../REPO

The agent can call get_task_context with the task and the files it will touch, propose decisions with propose_memory and report stale guidance with report_outdated. It can never approve: a different person approves each exact version on the Review page. The written client file holds local paths, never the credential. Launches were verified with the official MCP SDK client, not inside every coding application. To connect the importer workspace above by hand instead, follow the steps below.

The local MCP server also offers get_context. It returns approved guidance for an operator-bound repository, exact branch, and current validity interval.

First approve at least one decision with matching repository, exact branch, and currently active validity interval. Pending and legacy unscoped records are excluded. Use the importer agent ID printed by the public import (it already has local contributor and repository-read assignments), or create an agent principal and grant those assignments yourself in the sandbox.

Replace each uppercase placeholder below. The repository ID is GitHub's numeric ID, not owner/name; the project ID is MemoryNet's UUID. Run the command in the MemoryNet source directory:

mkdir -p .local/mcp
npm run mcp:binding -- .local/mcp/agent-main.json \
  AGENT_UUID PROJECT_UUID GITHUB_NUMERIC_REPO_ID EXACT_BRANCH

Stop the app, then restart it against the same trial database with the binding:

MEMORYNET_PROTOTYPE_CONFIG=off MEMORYNET_DATA_DIR=.data/personal-trial \
MEMORYNET_AGENT_BINDING_FILE="$PWD/.local/mcp/agent-main.json" npm run app

In your MCP host, add a stdio server with an absolute Node executable, an absolute path to src/scripts/mcp.ts, and these environment variables. Replace the example paths with your actual installation. Host-specific configuration still needs verification.

{
  "command": "/ABSOLUTE/PATH/TO/node",
  "args": ["/ABSOLUTE/PATH/TO/MemoryNet/src/scripts/mcp.ts"],
  "env": {
    "MEMORYNET_AGENT_BINDING_FILE": "/ABSOLUTE/PATH/TO/MemoryNet/.local/mcp/agent-main.json",
    "MEMORYNET_APP_URL": "http://127.0.0.1:3050"
  }
}

Ask the host to call get_context with a query about your approved decision. Check returned IDs, versions, citations, and applicability. An empty result can mean no approved scoped match; an authorization or transport error is a different outcome. This manually generated v1 binding retrieves context only. The v2 binding created by setup can also submit pending proposals and outdated reports; it never grants approval.

The owner-only binding expires after 24 hours and grants no database roles itself. Keep it private. This stdio bridge is local authorization, not remote OAuth. Run npm run eval:smoke for an isolated protocol check.

Keep a recoverable copy

Stop the app before backing up. Use a new destination for each operation:

MEMORYNET_DATA_DIR=.data/personal-trial npm run db:backup -- .local/backups/before-upgrade
npm run db:restore -- .local/backups/before-upgrade .data/recovered
MEMORYNET_PROTOTYPE_CONFIG=off MEMORYNET_DATA_DIR=.data/recovered npm run app

Backups contain the entire database and are not encrypted. Restore verifies file hashes, requires the matching PGlite version, and never overwrites an existing directory. Check the recovered records before switching databases.

A crash can leave a .memorynet-lock directory. Verify its recorded owner process has stopped before removing that lock. Never remove a live lock. app:reset permanently deletes a database; it is not record-level retention.

The production boundary

This is a local pilot. Shared or private-data production still requires:

  • Hosted identity, tenant membership, and remote agent delegation.
  • Signed GitHub ingestion and permission synchronization beyond signed-in users.
  • Record deletion, retention, backup expiry, and restore policy.
  • Supported deployment, monitoring, load testing, and recovery drills.

Product work also remains: automatic task notifications, persistent task-bound delivery, and verified spec-tool integration are partial or absent. Real-team benefit and repeat adoption have not been established.

The repository’s docs/production-readiness.md lists acceptance checks. GitHub Pages serves this website; it does not host the MemoryNet application.
